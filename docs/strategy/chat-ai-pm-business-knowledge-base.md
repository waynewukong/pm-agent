# AI 产品经理代理业务知识库模块

## 1. 模块定位

业务知识库模块负责把对话和交付物中真正有长期复用价值的 LTC 业务逻辑，沉淀到长期知识库中。

当前长期知识库固定放在：

`/Users/lzy/Documents/obsidian/zw的脑子/LTC业务知识库`

这个知识库不是页面资料库，也不是 PRD 摘要库，而是业务流转逻辑库。

## 2. 收录边界

### 2.1 应该沉淀

优先沉淀页面背后的业务逻辑：

- 业务对象定义：例如预实销记录、合格证申请记录
- 记录生成规则：记录由谁、什么动作、什么系统事件生成
- 生成前置条件：生成前必须满足哪些业务条件
- 初始状态：记录生成后进入什么状态
- 状态流转：状态之间如何变化，由什么动作触发
- 准入规则：什么条件下允许申请、提交、审批、取消、作废、完成
- 上下游关系：上游对象如何影响当前记录，当前记录如何触发下游流程
- 异常规则：重复生成、撤回、驳回、作废、失败等业务处理方式

### 2.2 默认不沉淀

以下内容默认不进入业务知识库：

- 页面展示字段
- 导出字段和列顺序
- 表格列、筛选项、按钮、弹窗、文案、布局
- 单次需求的页面方案或交互说明
- 可以直接在 LTC 页面上看到的表面信息
- 只影响 PRD、原型、测试用例写法的交付物结构

如果页面信息能够反推出业务流转规则，只记录背后的业务规则，不记录页面表现。

例子：

- 不沉淀：Excel 导出是否包含物料号
- 可沉淀：预实销记录生成时是否必须绑定车辆或 VIN
- 不沉淀：合格证申请列表展示哪些字段
- 可沉淀：合格证申请记录由谁发起，发起前必须满足哪些业务条件

## 3. 知识状态

每条业务知识必须标注状态：

- `已确认`：用户明确确认，或来自稳定业务规则
- `待补充`：已识别为重要业务知识，但尚未获得规则内容
- `假设`：为了推进方案先做的合理推断，不能当作确定规则复用
- `冲突待裁决`：新信息与旧知识不一致，不能直接覆盖
- `已废弃`：曾经成立，但后续被新规则替代

## 4. 自动沉淀流程

每轮需求协作按以下顺序执行：

1. 解析用户输入和已有交付物
2. 先判断是否出现业务对象、生成规则、流转规则、状态规则或上下游因果
3. 排除页面字段、导出字段、布局、交互等非业务知识
4. 读取 Obsidian 知识库中相关业务对象和流程卡片
5. 判断候选知识是新增、补充、确认、冲突还是待补充
6. 更新对应业务对象、业务流程、业务规则或待补充清单
7. 更新知识变更日志

当前 chat-first 阶段的“自动”，指代理在每次需求处理和文档修订时主动执行上述动作；后续实现 PM Agent 时，再把这套流程固化为代码。

## 6. 合并规则

### 6.1 新业务对象

如果对话中出现新的核心业务对象：

- 新建业务对象卡片
- 建立对应的“生成与流转”流程卡片
- 如果规则未知，状态标为 `待补充`
- 在待补充清单中记录需要追问的问题

### 6.2 新生成或流转规则

如果用户补充了记录生成、状态流转或上下游影响：

- 更新对应业务流程卡片
- 如果规则足够稳定，写入业务规则索引
- 记录来源和确认状态

### 6.3 页面信息过滤

如果新信息只是页面字段、导出字段、列顺序或布局：

- 不写入业务知识库
- 只保留在当前 PRD、原型说明或测试用例中
- 如果它暗示业务规则，先追问或转写为背后的业务规则

### 6.4 规则冲突

如果新信息与已有业务规则冲突：

- 不直接覆盖原知识
- 在原卡片标注冲突提示
- 在待补充清单新增裁决项
- 等用户确认后再更新

## 8. 与交付物的关系

PRD、原型说明和测试用例仍然承接单次需求的页面、字段、导出和交互方案。

业务知识库只承接跨需求复用的业务流转逻辑。

当两者存在关系时：

- PRD 可以引用知识库中的生成规则、状态规则和上下游规则
- PRD 新增的页面字段或导出字段不自动进入知识库
- PRD 新确认的业务生成或流转规则必须同步进入知识库
- 测试用例应覆盖本需求涉及的已确认业务规则

## 9. 触发条件

出现以下情况时必须更新业务知识库：

- 用户明确说明某类记录如何生成
- 用户明确说明某个业务对象的前置条件
- 用户明确说明状态变化、审批、驳回、取消、作废或完成规则
- 用户明确说明上游数据如何影响当前业务对象
- 用户明确说明当前业务对象如何触发下游流程
- 新需求暴露出已有业务规则冲突
- 某个待补充问题被用户确认

出现以下情况时默认不更新业务知识库：

- 只是新增页面列
- 只是新增导出字段
- 只是调整筛选项、按钮、弹窗或展示文案
- 只是补充原型或测试用例的交付物细节
