# AI 产品经理代理行动计划

## 1. 总体策略

采用 `先走路线 2，但以路线 1 的方式启动`：

- 短期先直接和 AI 协作，验证是否真的好用
- 中期把协作过程沉淀成规则、模板和状态机
- 后期再把这套规则固化成真正可复用的 PM Agent

换句话说：

- 现在先用
- 边用边定义
- 定义稳定后再实现

## 2. 阶段划分

### Phase 0：先把协作方式跑通

#### 目标

验证“你直接和我对话，我来澄清需求并输出交付物”是否真的高效。

#### 要做的事

1. 选 3 到 5 个真实需求作为样本
2. 直接通过对话完成需求澄清
3. 输出 PRD、原型说明、测试用例
4. 记录每次协作中：
   - 哪些追问最有价值
   - 哪些信息总是缺失
   - 哪些输出最容易返工
   - 哪些地方最依赖临场判断

#### 产出

- 一组真实需求样本
- 每个样本对应的交付物
- 一份初步经验记录

#### 完成标志

至少有 3 个真实案例能顺利从原始描述走到可用交付物。

### Phase 1：沉淀收敛规则

#### 目标

把“我现在是怎么做需求澄清和信息收敛的”定义成稳定规则。

#### 要做的事

1. 明确输入类型
2. 定义结构化需求模型
3. 定义字段收敛规则
4. 定义何时追问、何时假设、何时生成
5. 定义修订模式下的增量更新规则

#### 当前状态

这部分已经开始，且已有文档基础。

#### 产出

- `对话式 AI 产品经理代理方案`
- `对话输入到结构化需求模型的收敛规则`

#### 完成标志

面对同类型需求时，结构化字段命名和收敛方式基本稳定。

### Phase 2：沉淀追问与输出协议

#### 目标

把“我该怎么问、每轮该怎么回”做成清晰协议。

#### 要做的事

1. 定义追问优先级
2. 定义每轮最多问几个问题
3. 定义不同状态下的标准回应结构
4. 定义“直接出方案”时的默认处理方式
5. 定义“改一下”时的修订回应格式

#### 产出

- `追问策略与输出协议`

#### 完成标志

在 intake、clarify、generate、revise 四类场景下，都有稳定回应格式。

### Phase 3：沉淀交付物模板

#### 目标

让 PRD、原型说明、测试用例的输出结构稳定下来，减少每次从头组织。

#### 要做的事

1. 定义 PRD 标准模板
2. 定义原型说明模板
3. 定义测试用例模板
4. 定义待确认项和假设的标注方式
5. 定义修订记录格式

#### 产出

- `PRD 模板`
- `原型说明模板`
- `测试用例模板`
- `修订记录模板`

#### 完成标志

交付物结构统一，样本需求的输出风格基本一致。

### Phase 4：手工代理阶段持续验证

#### 目标

在不写 Agent 代码之前，继续用“人 + AI 代理”的方式跑，确认规则是否真的够用。

#### 要做的事

1. 用新需求持续验证前面沉淀的规则
2. 发现例外情况并补规则
3. 识别哪些动作适合代码化，哪些仍然要保留模型判断
4. 记录高频任务和标准动作

#### 产出

- 规则补丁
- 异常场景清单
- 适合代码化的动作清单

#### 完成标志

你已经能明显感觉到这套协作方式稳定、顺手、可复用。

### Phase 4.5：建立业务知识库自动沉淀机制

#### 目标

让真实需求中关于业务对象生成、状态流转、准入条件和上下游因果的知识，不只停留在单次 PRD 里，而是持续沉淀到 LTC 业务知识库。

#### 要做的事

1. 建立 Obsidian 知识库目录
2. 定义业务知识卡片结构
3. 定义每轮对话后的纯业务知识抽取和合并规则
4. 定义已确认、假设、待确认、冲突待裁决、已废弃等状态
5. 建立预实销记录、合格证申请记录等业务对象的待补充卡片
6. 后续每次需求协作都同步更新知识库

#### 产出

- `业务知识库模块规则`
- `LTC 业务知识库`
- 第一批业务对象、业务流程、业务规则和待补充清单

#### 完成标志

每次新需求或需求修订后，都能明确回答：“这轮对话新增、确认、修改或冲突了哪些业务知识，并已沉淀到哪里。”

### Phase 5：设计 PM Agent 的系统结构

#### 目标

把前面沉淀下来的工作方式真正转成 agent 设计。

#### 要做的事

1. 设计状态机
2. 设计 Requirement Model 数据结构
3. 设计消息输入和输出格式
4. 设计工具编排方式
5. 设计文件保存与版本管理方式
6. 设计业务知识库读写和冲突处理方式
7. 设计修订模式下的影响传播机制

#### 产出

- Agent 架构设计稿
- 状态机定义
- 数据结构定义
- 工具调用流程图

#### 完成标志

已经可以明确回答：“如果开始写 agent，核心模块有哪些、输入输出是什么、由谁负责什么”。

### Phase 6：实现第一版 PM Agent

#### 目标

把已有规则写成代码和流程，让它不依赖当前这次对话也能运行。

#### 要做的事

1. 实现输入解析层
2. 实现结构化需求模型更新逻辑
3. 实现业务知识抽取与合并逻辑
4. 实现追问生成逻辑
5. 实现 PRD / 原型 / 测试用例生成流程
6. 实现文档保存逻辑
7. 实现修订模式

#### 产出

- 第一版 PM Agent
- 最小可运行流程
- 一组回归验证样例

#### 完成标志

给 agent 一段原始需求后，它能独立完成第一轮澄清和第一版交付物生成。

### Phase 7：决定是否产品化

#### 目标

在 agent 能稳定跑之后，再决定是否做成独立产品。

#### 要做的事

1. 判断是否有多人使用需求
2. 判断是否需要会话管理、版本对比、权限管理
3. 判断是否值得做前端工作台
4. 判断是否需要额外模型分层和成本控制

#### 产出

- 产品化决策结论
- 产品边界草案

#### 完成标志

能够明确回答：“我们只是继续用 agent，还是值得进入产品化开发”。

## 3. 近期最优先事项

如果只看接下来 1 到 2 周，最值得做的是：

1. 用真实需求继续直接协作，积累 3 到 5 个样本
2. 每次真实需求都同步更新 LTC 业务知识库
3. 继续验证 `追问策略与输出协议`
4. 继续验证 `PRD / 原型说明 / 测试用例` 模板
5. 用新需求反复验证这些规则

## 4. 你和我各自的任务

### 你负责

1. 持续给我真实需求样本
2. 明确指出哪些输出让你觉得“有用”或“没打中”
3. 告诉我哪些追问太多、太少或不关键
4. 帮我判断哪些交付物最值得保留

### 我负责

1. 继续扮演 AI 产品经理代理
2. 在协作中沉淀规则和模板
3. 从对话和交付物中抽取可复用业务知识
4. 将业务知识同步维护到 LTC 业务知识库
5. 把隐性的判断过程显性化成文档
6. 在规则稳定后进一步设计 Agent 架构

## 5. 风险提醒

### 风险 1：过早工程化

如果样本还不够，就急着写 agent，容易把错误流程固化。

### 风险 2：过度依赖临场发挥

如果只靠每次临场判断，不沉淀规则，后面很难复用。

### 风险 3：过早做前端产品

如果代理工作流还没稳定，就先做产品壳，很容易做出表面完整、内核不稳的系统。

### 风险 4：知识库只新增不治理

如果只把信息堆进知识库，而不做状态、来源、冲突和废弃管理，后续会变成不可复用的资料堆。

## 6. 建议的执行顺序

最推荐的顺序是：

1. 继续直接和我协作
2. 同步沉淀规则和业务知识
3. 固化模板
4. 用样本反复验证
5. 设计 Agent
6. 再决定是否产品化

## 7. 当前结论

你现在不该优先去接别的模型 API，也不该先做聊天前端。

你现在最应该做的是：

`把我当作正在工作的 AI 产品经理，同时让我帮你把这个工作方式沉淀成未来可复用的 PM Agent。`
