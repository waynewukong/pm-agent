# 对话输入到结构化需求模型的收敛规则

## 1. 文档目的

这份文档用来定义：

- 用户在对话里给出自然语言需求后，我应该如何理解
- 我应该如何把非结构化描述收敛成统一的需求模型
- 在什么情况下要追问
- 在什么情况下可以先做假设
- 什么时候可以开始输出 PRD、原型、测试用例

它服务的对象不是前端页面，而是 `AI 产品经理代理本身的工作协议`。

## 2. 总体原则

- `先理解主题，再拆业务`
- `先抓主链路，再补细节`
- `先形成可用模型，再追求完整模型`
- `默认收敛，不默认停住`
- `能做假设时先做假设，但要显式标记`
- `追问只服务于更高质量输出，不为了问全`

## 3. 输入来源

用户输入可能来自以下几类信息：

- 原始自然语言描述
- 页面截图说明
- 现有 PRD 或方案片段
- 用户对上一版输出的修改意见
- 零散的业务背景补充

这些输入不要求完整，也不要求顺序一致。

## 4. 收敛目标

每一轮对话结束时，我都应该尽量把输入收敛成一个统一模型：

```json
{
  "meta": {
    "title": "",
    "type": "",
    "scenario": "",
    "stage": "",
    "confidence": 0
  },
  "actors": [],
  "goal": "",
  "painPoints": [],
  "pages": [],
  "rules": [],
  "knowledgeCandidates": [],
  "assumptions": [],
  "openQuestions": [],
  "artifacts": {
    "prdReady": false,
    "prototypeReady": false,
    "testCasesReady": false
  }
}
```

这个模型不要求第一次就完整，但必须越来越完整。

## 5. 字段收敛规则

### 5.1 meta.title

#### 识别方法

- 优先取用户明确说出的需求标题
- 如果用户没有标题，则用“场景 + 动作/目标”生成一个工作标题
- 标题要能反映主问题，而不是照抄整段描述

#### 例子

- 用户说：“想优化报价审批效率”
- 收敛标题：`报价审批链路效率优化`

### 5.2 meta.type

#### 可选类型

- `optimize`：优化现有功能
- `new`：新增模块/能力
- `fix`：偏问题修复
- `research`：方案研究或需求探索

#### 判断规则

- 出现“优化、提升、缩短、减少跳转、改版”等词，优先判为 `optimize`
- 出现“新增、新建、搭一个模块、从 0 开始”等词，优先判为 `new`
- 出现“异常、错误、bug、修复、对不上”等词，优先判为 `fix`
- 出现“先帮我分析、先别出方案、帮我研究一下”等词，优先判为 `research`

#### 冲突处理

如果同时出现新增和优化，优先判断本期主目标：

- 主目标是改善现有链路，则记为 `optimize`
- 主目标是建设新能力，则记为 `new`

### 5.3 meta.scenario

#### 识别内容

场景不是页面名，而是业务行为发生的业务上下文。

#### 例子

- `LTC 报价审批`
- `销售顾问提交报价后的审批协同`
- `门店线索分配与跟进`

#### 处理规则

- 用户明确提到业务环节时直接采用
- 如果只提页面不提业务，则从页面目标反推一个暂定场景
- 反推得到的场景必须进 `assumptions`

### 5.4 actors

#### 识别内容

actors 是实际参与流程的人或角色，不是系统模块。

#### 常见来源

- “销售顾问”
- “审批人”
- “运营”
- “门店经理”
- “财务”

#### 收敛规则

- 能明确识别就直接收敛
- 用户说“不同角色看到的不一样”时，要标记角色差异为高优先级待确认项
- 如果只有一个模糊称谓，例如“业务人员”，先保留原文，不擅自细分

### 5.5 goal

#### 识别内容

goal 是这次需求最想改善的结果，不是页面动作本身。

#### 提取优先顺序

1. 用户直接表达的目标
2. 从痛点反推目标
3. 从场景默认目标推断

#### 目标写法要求

尽量写成“改善什么结果”，而不是“做什么功能”。

#### 好例子

- `缩短报价审批关键路径`
- `提升驳回原因透明度`
- `降低销售顾问定位问题的时间成本`

### 5.6 painPoints

#### 识别内容

painPoints 是当前问题，不是未来方案。

#### 拆分规则

- 一段长描述要拆成离散问题
- 每个问题最好只表达一个核心障碍
- 同类问题可以聚合，但不能混成一句大话

#### 例子

原始输入：

“现在得先去列表找，再进详情，再去审批记录里翻驳回原因，很慢。”

收敛后：

- 列表页无法直接识别审批关键状态
- 驳回原因需要进入详情页后再次查找
- 定位审批记录路径过长

### 5.7 pages

#### 识别内容

pages 既可以是页面，也可以是关键流程节点或弹窗，只要它在方案里承担稳定职责。

#### 页面对象最小字段

```json
{
  "name": "",
  "type": "",
  "currentState": "",
  "targetChange": "",
  "pageGoal": "",
  "roles": [],
  "linkage": "",
  "risk": "medium",
  "evidence": []
}
```

#### 收敛规则

- 用户明确提到页面时，直接建对象
- 用户提到动作节点，例如“审批弹窗”，也视为页面对象
- 截图对应的页面要记录到 `evidence`
- 不清楚名称时，可以先用工作名，例如“报价详情页（待确认）”

#### type 建议枚举

- `list`
- `detail`
- `form`
- `approval`
- `dashboard`
- `modal`
- `flow-node`

### 5.8 rules

#### 识别内容

rules 是业务规则、状态规则、显示规则、权限规则。

#### 常见触发句

- “只有审批通过后才能...”
- “不同角色看到的内容不同”
- “驳回原因要保留历史记录”
- “状态要统一”

#### 规则收敛方法

- 先记事实，不急着抽象成复杂规则树
- 一条规则尽量只表达一件事
- 如果规则影响多个页面，要标记 `cross-page`

### 5.8.1 knowledgeCandidates

#### 识别内容

knowledgeCandidates 是本轮对话中可能需要进入长期业务知识库的候选知识。

#### 候选类型

- 业务对象
- 业务流程
- 记录生成规则
- 状态流转规则
- 准入和限制规则
- 上下游关系
- 待确认知识

#### 收敛规则

- 只记录页面背后的业务逻辑，不记录页面展示本身
- 能从用户明确表述或已确认交付物中得到的，标记为 `已确认`
- 为推进方案做出的推断，标记为 `假设`
- 会影响后续方案但未确认的，标记为 `待确认`
- 与历史知识冲突的，标记为 `冲突待裁决`
- 需要沉淀的内容统一写入 `/Users/lzy/Documents/obsidian/zw的脑子/LTC业务知识库`
- 页面字段、导出字段、列顺序、筛选项、按钮和布局默认不进入知识库

### 5.9 assumptions

#### 什么时候可以写假设

- 用户没有给出，但不影响先出第一版
- 行业内有明显默认做法
- 从上下文可以较高概率推断

#### 假设必须包含

- 假设内容
- 为什么这么假设
- 影响什么输出
- 是否需要用户确认

#### 例子

- 假设：本期改动范围包含报价列表页、详情页和审批弹窗
- 原因：用户多次提到这三处的跳转问题
- 影响：PRD 范围、原型页数、测试用例范围
- needConfirmation：true

### 5.10 openQuestions

#### 什么问题应该进 openQuestions

- 会显著影响方案范围
- 会影响角色差异设计
- 会影响规则或验收口径
- 无法安全默认推断

#### 不该进入的

- 纯措辞问题
- 对第一版产出影响很小的问题
- 可以在开发评审阶段再确认的问题

## 6. 收敛流程

### 6.1 第一步：识别主题

先回答三个问题：

1. 这件事在讲什么
2. 它属于什么类型需求
3. 它的主目标是什么

如果这三点都没抓住，不进入后续生成。

### 6.2 第二步：识别业务骨架

抽取：

- 场景
- actors
- 主流程
- 页面/节点
- 关键痛点

这一步的目标是形成一个粗粒度主链路。

### 6.3 第三步：识别设计约束

抽取：

- 状态规则
- 权限差异
- 范围边界
- 历史兼容
- 数据展示约束

### 6.4 第四步：判断是否追问

如果以下任一项不清晰，则优先追问：

- 本期范围
- 主目标
- 关键角色差异
- 核心状态规则
- 最重要的验收方式

### 6.5 第五步：形成第一版结构化模型

此时不要求完整，但必须可用于：

- 生成需求摘要
- 生成第一轮问题
- 判断能否开始输出 PRD

### 6.6 第六步：决定输出策略

- 信息足够：直接生成第一版交付物
- 信息部分缺失：带假设生成第一版交付物
- 信息严重不足：只输出理解摘要和追问，不硬生成

## 7. 追问判定规则

### 7.1 必问项

以下情况通常要问：

- 页面范围可能大幅变动
- 多角色是否差异化展示不明确
- 核心规则存在多种实现路径
- 用户要“直接出方案”，但目标都还不清晰

### 7.2 可不问项

以下情况通常可以先假设：

- 页面名称不规范
- 文案细节未定
- 次要字段未明确
- 非关键异常场景暂未补充

### 7.3 问题数量

每轮最多 3 个。

优先级排序公式可以简单定义为：

`影响范围 x 阻塞程度 x 不确定性`

只问分值最高的问题。

## 8. 生成门槛

### 8.1 可以开始生成 PRD 的条件

至少有：

- title
- type
- scenario
- goal
- actors
- 至少一个页面或模块对象
- 至少两个有效 painPoints

### 8.2 可以开始生成原型说明的条件

至少有：

- 页面或模块对象
- 页面目标或主要改动方向
- 主链路

如果需求涉及存量页面优化，进入原型说明前还需要先向用户索要页面截图。

截图要求：

- 至少包含本次改动涉及的主页面
- 如果涉及弹窗、抽屉、详情页或异常状态，需要同步索要对应截图
- 如果用户暂时无法提供截图，可以先输出低保真页面结构说明，但不进入高保真 Figma 原型

高保真原型生成门槛：

- 已收到关键页面截图，或用户明确提供可替代的参考页面 / 设计规范
- PRD 骨架中的目标、范围、页面对象和关键规则已经确认
- 页面新增、修改、删除的字段或操作已经可描述

满足以上条件后，原型阶段默认调用 Figma MCP 生成高保真原型。

### 8.3 可以开始生成测试用例的条件

至少有：

- 主要功能点
- 页面对象
- 至少一条规则或状态说明

## 9. 修订模式下的收敛规则

用户进入“改一下”模式后，不再重建全模型，而是做增量更新。

### 9.1 识别修改意图

优先判断用户在改什么：

- 改目标
- 改范围
- 改页面方案
- 改业务规则
- 改输出形式

### 9.2 更新原则

- 只更新受影响字段
- 记录 changeLog
- 标记被影响的交付物
- 优先局部修订，不整份重写

### 9.3 影响传播

例如用户说：

“审批弹窗不改了，只改列表页和详情页。”

则至少影响：

- pages 范围
- PRD 的范围章节
- 原型页数
- 测试用例覆盖范围
- 风险评估

## 10. 输出协议

每轮对话后，我内部都应该能整理出以下四类输出：

### 10.1 理解摘要

当前我如何理解这个需求。

### 10.2 结构化增量

本轮新增确认了哪些字段。

### 10.3 待确认项

还有哪些问题值得下一轮继续问。

### 10.4 交付动作

这一轮应该：

- 只追问
- 追问并给摘要
- 直接生成第一版
- 基于反馈修订

## 11. 一个完整示例

### 11.1 用户原始输入

“我们现在报价审批太绕了，销售要来回切页面看驳回原因，审批人也不方便判断，想优化一下。主要是报价列表、报价详情和审批弹窗这几个地方。”

### 11.2 第一轮收敛

- title：`报价审批链路效率优化`
- type：`optimize`
- scenario：`报价审批`
- actors：`销售顾问、审批人`
- goal：`缩短审批操作路径并提升驳回原因透明度`
- painPoints：
  - 列表页无法直接查看关键审批状态
  - 销售需要跨页面查找驳回原因
  - 审批人在弹窗内缺少足够判断信息
- pages：
  - 报价列表页
  - 报价详情页
  - 审批弹窗

### 11.3 第一轮追问

1. 本期这三个页面都要改，还是有主次范围？
2. 驳回原因需要在列表页直接展示摘要，还是只提供快捷入口？
3. 销售和审批人看到的信息是否一致？

### 11.4 生成判断

虽然还有待确认项，但已经满足第一版 PRD 和原型说明的最低条件，可以先生成，再带着待确认项修订。

## 12. 落地要求

如果这套规则后续要真正作为我的执行协议，至少要满足：

- 每轮对话都能回写结构化模型
- 结构化字段命名稳定
- 假设和事实严格区分
- 待确认项有优先级
- 修订是增量而不是重算一切

## 13. 下一步建议

在这份规则之后，下一份最该补的是：

1. `追问策略与输出协议`
2. `PRD 标准模板`
3. `原型说明模板`
4. `测试用例模板`

这样整个 AI 产品经理代理就从“有思路”进入“有执行标准”。
