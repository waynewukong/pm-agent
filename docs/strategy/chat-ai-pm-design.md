# 对话式 AI 产品经理代理方案

## 1. 方案定义

这不是一个“先做聊天前端产品”的方案。

这是一个 `以 AI 助手为核心的产品经理代理模式`：

- 你直接和我对话
- 你给我原始需求、截图、补充背景、修改意见
- 我负责像产品经理一样追问、澄清、收敛
- 我在后台调用工具和模板
- 我最终给你产出 `PRD`、`原型`、`测试用例`，必要时继续修订

所以，这个方案的核心不是“做一个聊天 UI”，而是 `先定义一个可持续工作的 AI 产品经理工作流`。

## 2. 产品本质

### 2.1 一句话定义

一个通过多轮对话完成 `需求澄清 -> 结构化建模 -> 交付物生成 -> 增量修订` 的 AI 产品经理代理。

### 2.2 核心价值

- 你不用先写完整 PRD
- 你不用自己先把需求整理成结构化表单
- 你可以直接发散地表达
- 我负责把非结构化信息变成可交付产物
- 你可以持续通过自然语言修改，不需要重新开文档重写

### 2.3 适合的任务

- 存量系统优化需求
- 多页面联动需求
- 截图驱动的现状分析
- 新模块初版设计
- 需求评审前的方案整理
- 开发前的测试点补全

## 3. 角色分工

### 3.1 你负责

- 提供原始需求
- 提供上下文和约束
- 上传截图、流程、资料
- 回答我提出的关键问题
- 对输出结果给修改意见

### 3.2 我负责

- 理解需求并主动发现歧义
- 识别范围、角色、流程、规则、风险
- 提出最少但最关键的追问
- 形成结构化需求模型
- 生成交付物
- 根据反馈增量修订交付物
- 在必要时调用工具补齐产出

### 3.3 工具负责

- 保存中间文档
- 生成结构化内容
- 生成原型代码或原型稿
- 整理测试用例
- 做必要的文件输出与版本留存

## 4. 工作方式

### 4.1 总体模式

整体模式是：

1. 你说需求
2. 我追问澄清
3. 我收敛成结构化模型
4. 我调用工具生成交付物
5. 你继续提反馈
6. 我做定向修订

### 4.2 交互原则

- `对话优先`
- `结构化在后台完成`
- `每轮都要有收敛结果`
- `优先追问高价值信息`
- `能默认补齐的先补齐`
- `输出必须可继续修改`

### 4.3 为什么这样更适合你

因为你真正想要的，不是再维护一个前端工作台，而是：

- 直接把想法告诉我
- 让我像产品经理一样推进
- 让我自己去调工具完成后续动作

也就是说，前台体验就是 `你和我对话`，系统能力则体现在我背后的编排和产出能力里。

## 5. 核心流程

### 5.1 主流程

1. `接收原始输入`
2. `识别需求类型`
3. `生成第一版理解摘要`
4. `提出关键追问`
5. `形成结构化需求模型`
6. `生成交付物`
7. `根据反馈修订`
8. `沉淀最终版本`

### 5.2 三个核心动作

- `澄清需求`
- `生成交付物`
- `根据反馈修订`

这三个动作就是整个代理方案的主心骨。

## 6. 对话状态机

### 6.1 状态定义

- `intake`：接收需求
- `clarify`：补关键缺口
- `structure`：整理成需求模型
- `generate`：输出交付物
- `revise`：按反馈修订
- `finalize`：确认当前版本可用

### 6.2 状态切换逻辑

- 用户只给原始描述时，进入 `intake`
- 信息不够支持稳定输出时，进入 `clarify`
- 关键信息已够时，进入 `structure`
- 需要产出 PRD / 原型 / 用例时，进入 `generate`
- 用户说“改一下”时，进入 `revise`
- 当前版本满足使用时，进入 `finalize`

### 6.3 最小生成条件

达到以下条件即可开始第一版生成：

- 有主题
- 有业务场景
- 有目标或痛点
- 有用户角色或操作主体
- 有至少一个页面、流程节点或模块对象

如果条件不完整，我也可以带着默认假设先出第一版，但必须标记待确认项。

## 7. 后台结构化模型

虽然你前台只是在和我聊天，但我后台需要维护一个持续更新的需求模型。

```json
{
  "meta": {
    "title": "",
    "type": "optimize | new | fix | research",
    "scenario": "",
    "stage": "clarify | generate | revise",
    "confidence": 0
  },
  "actors": [],
  "goal": "",
  "painPoints": [],
  "pages": [],
  "rules": [],
  "assumptions": [],
  "openQuestions": [],
  "artifacts": {
    "prd": null,
    "prototype": null,
    "testCases": null
  },
  "changeLog": []
}
```

### 7.1 pages 建议字段

- `name`
- `type`
- `currentState`
- `targetChange`
- `pageGoal`
- `keyFields`
- `keyActions`
- `roles`
- `linkage`
- `risk`
- `evidence`

### 7.2 openQuestions 建议字段

- `question`
- `reason`
- `blocking`
- `priority`
- `relatedOutput`

### 7.3 assumptions 建议字段

- `content`
- `reason`
- `impact`
- `needConfirmation`

## 8. 追问机制

### 8.1 追问目标

追问不是为了把所有信息问全，而是优先解决那些会直接影响方案质量和交付物准确性的缺口。

### 8.2 优先级规则

优先追问：

1. 范围
2. 目标
3. 角色差异
4. 页面链路
5. 状态和规则
6. 验收口径

### 8.3 追问原则

- 每轮最多 3 个问题
- 问题要尽量短
- 问题要说明为什么问
- 能自己推断的不问
- 能先产出后确认的不阻塞

### 8.4 理想的追问风格

不是问卷式：

- “请补充以下 12 项信息”

而是产品经理式：

- “我先按报价审批链路优化来理解。现在最影响方案质量的有两点：一是本期到底改哪些页面，二是驳回原因要不要聚合展示。我先问这两个，确认后我就能直接出第一版 PRD。”

## 9. 交付物体系

### 9.1 PRD

PRD 是主交付物，建议固定结构：

1. 背景与目标
2. 现状与问题
3. 用户与角色
4. 范围与边界
5. 页面 / 模块方案
6. 业务规则
7. 交互说明
8. 风险与依赖
9. 验收标准
10. 开发与测试关注点

### 9.2 原型

原型可以分两层：

- 第一层：页面级方案描述
- 第二层：基于截图的高保真 Figma 原型

第一阶段先由我生成：

- 页面结构
- 信息优先级
- 关键组件
- 页面跳转关系
- 重点状态展示

进入原型阶段时，默认流程调整为：

1. 我先向你索要当前业务页面截图，必要时说明需要哪些页面、状态或弹窗截图
2. 我基于截图识别现有布局、字段、操作入口和视觉约束
3. 我先输出原型说明，确认页面结构、信息层级、交互和状态
4. 我调用 Figma MCP 生成高保真原型
5. 我把 Figma 原型结果与 PRD、测试用例保持同一版本

如果是全新页面，没有现有截图，则改为索要参考页面、竞品截图或业务系统设计规范，再进入 Figma 原型输出。

### 9.3 测试用例

测试用例要跟着需求模型自动延展，至少覆盖：

- 页面内功能验证
- 页面间联动验证
- 角色差异验证
- 状态流转验证
- 历史兼容验证
- 异常与空态验证

## 10. 输出策略

### 10.1 首轮输出

用户第一次说完需求后，我应该尽快给出：

- 我当前的理解摘要
- 我认为的需求类型
- 当前缺的关键信息
- 下一轮最值得回答的问题

### 10.2 满足生成条件后

我应该开始给出：

- 第一版 PRD
- 第一版原型说明
- 第一版测试用例

### 10.3 信息不足时

如果你说“直接出”，我的策略应该是：

- 用合理假设补齐
- 明确写出假设
- 标记待确认项
- 不因为信息不完整就完全停住

### 10.4 用户反馈后

我不应该整份重写，而应该输出：

- 改动摘要
- 影响范围
- 已同步更新的交付物部分
- 仍待确认的事项

## 11. 工具编排

### 11.1 编排原则

- 对你来说，工具应该是隐形的
- 对我来说，工具是完成交付的执行层
- 工具调用应该围绕交付物，而不是围绕表单字段

### 11.2 可调用的工具类型

- 文档生成工具
- 原型生成工具
- 测试用例整理工具
- 文件保存工具
- 业务知识库更新工具
- 图像或截图处理工具

### 11.3 一次典型编排

当你发来“报价审批链路效率优化”并附几张页面截图时，我的内部动作可以是：

1. 解析你的描述
2. 抽取页面与角色
3. 形成第一版需求模型
4. 生成追问
5. 在你回答后生成 PRD
6. 调用原型生成能力产出页面方案
7. 同步生成测试用例
8. 抽取并更新 LTC 业务知识库
9. 保存到本地文件，便于后续继续修改

## 12. 文档与业务知识记忆机制

### 12.1 为什么要保存

虽然交互入口是聊天，但需求工作不是一次性行为，所以必须有可持续的文档载体。

### 12.2 建议保存的内容

交付物层面保存：

- 最新需求摘要
- 当前结构化模型
- 最新 PRD
- 最新原型说明
- 最新测试用例
- 修订记录

业务知识层面保存：

- 业务对象
- 记录生成规则
- 生成前置条件
- 状态流转规则
- 准入和限制规则
- 上下游因果关系
- 异常业务分支
- 业务规则
- 待确认知识

### 12.3 保存原则

- 每次大改后保存快照
- 保存“当前最新版本”，避免文件散乱
- 必要时再保留历史版本
- 文件名尽量稳定，便于在下一轮继续接上

### 12.4 业务知识库位置

长期业务知识统一保存到：

`/Users/lzy/Documents/obsidian/zw的脑子/LTC业务知识库`

本项目只保存业务知识库模块规则，不把长期业务知识散落在 `docs/` 中。

### 12.5 自动沉淀要求

每次需求对话或交付物修订后，我都要判断是否产生了可复用业务知识：

- 新业务对象要进入对象库
- 新记录生成规则要进入业务流程卡片
- 新状态流转规则要进入业务流程或业务规则卡片
- 新上下游因果关系要进入业务对象或流程卡片
- 未确认和冲突信息要进入待补充清单

如果新知识与旧知识冲突，不直接覆盖旧知识，而是标记为冲突待裁决。

页面展示字段、导出字段、列顺序、筛选项和按钮布局默认不进入业务知识库，只保留在对应交付物中。

## 13. 这个方案和“做聊天产品前端”的区别

前者是：

- 我就是主界面
- 你直接和我协作
- 重点是代理能力、追问能力、产出能力、修订能力

后者是：

- 先做一个聊天应用
- 再把 AI 能力嵌进去

你现在要的明显是前者。

所以当前阶段的正确顺序不是：

1. 先做聊天前端
2. 再设计 AI 产品经理

而应该是：

1. 先把 AI 产品经理的工作流定义清楚
2. 先验证我是否能稳定地产出
3. 如果以后有必要，再把这套能力封装成产品前端

## 15. 推荐的实际执行方式

如果按你现在的想法推进，最合理的工作方式应该是：

1. 你在对话里直接给我需求
2. 我先做需求澄清和收敛
3. 我调用工具输出文档
4. 你继续在对话里给反馈
5. 我继续修订文档、原型和 LTC 业务知识库

也就是说，这个项目的“产品”首先不是一个网页，而是 `一套以我为核心的 AI 产品经理协作机制`。

## 16. 下一步建议

下一步不该先改前端，而应该先补下面四样东西：

1. `对话输入 -> 结构化需求模型` 的收敛规则
2. `追问策略` 和 `输出协议`
3. `业务知识库自动沉淀` 的执行规则
4. `PRD / 原型 / 测试用例` 的标准模板

这些定下来之后，我们再决定是否需要把它做成单独产品界面。
